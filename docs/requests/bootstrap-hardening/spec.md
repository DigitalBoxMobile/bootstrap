# Hardening публикации и контракта перед iOS-интеграцией — спецификация

Статус: `ready for implementation`

Источник: внешний аудит репозитория на `dbc5dce` (2026-11-02), находки F1–F5 и уточнения контракта 1–4.
F4 (недоступные зеркала) закрыт до пакета: манифесты `version 3`, три зеркала, `bin/check-mirrors` выход `0`.
Архитектура — `docs/adr/0001-signed-bootstrap-manifests.md`; контракт — `docs/client-contract.md`.

## Что и зачем

Публикация не должна менять на зеркале то, что не проверила и не показала в отчёте (F1), и не должна откатывать
зеркало при конкурентных издателях (F2). Повреждённое или враждебное зеркало не должно ронять мониторинг и preflight (F3).
`bin/check` не должен падать с traceback на несуществующей дате (F5). Контракт клиента должен однозначно отвечать
на вопросы, которые иначе решит каждая платформа по-своему (уточнения 1–4).

## F1. Git-зеркало и фильтр `--env`

Git-цель публикует весь `HEAD`, поэтому для неё фильтр `--env` не может сузить набор изменяемых файлов.

- Для цели `type: git` набор проверяемых env — **все** env из `manifests/`, независимо от `--env`.
- Preflight (чтение `public_url`, `unchanged` / `rollback_refused` / `upload`) и проверка после записи выполняются
  для каждого env, чьи байты на зеркале отличаются от `dist/`; каждая такая строка попадает в итоговую таблицу.
- Если `--env` задан и хотя бы один **не выбранный** env на git-зеркале отличается от `dist/` — цель не пушится,
  строки этих env получают `error: env_filter_conflict`, выход `1`. Остальные цели (s3) работают по `--env` как раньше.
- `rollback_refused` по любому env git-цели отменяет push целиком (как сейчас для цели).

## F2. Условная запись на S3

Yandex Object Storage и Selectel поддерживают условный `PutObject` (проверено 2026-11-02 на живых бакетах:
неверный `If-Match` и `If-None-Match: *` на существующий объект → `412 PreconditionFailed`, верный `If-Match` → запись).

- Preflight читает объект через `GetObject` с учётными данными и запоминает `ETag`.
- Запись: объект был → `PutObject(..., IfMatch=<ETag из preflight>)`; объекта не было → `IfNoneMatch="*"`.
- `412` → строка `error: conflict` (объект изменился между чтением и записью; повторить публикацию), выход `1`;
  остальные env и цели продолжаются.
- `--dry-run` без учётных данных по-прежнему читает `public_url` и ничего не пишет; ETag там не нужен.
- Git-цель уже атомарна: push без force отклоняется, если удалённая ветка не является предком `HEAD`.

## F3. Устойчивость к ответу зеркала

- `bootstrap/http.get` читает тело потоково и прекращает чтение после **65536 байт**: результат — отдельный код
  `oversized` (как `unreachable`, это проблема зеркала, не исключение).
- Разбор JWS и payload в `contract.evaluate`: `RecursionError` (и любое другое исключение разбора JSON) → `malformed`.
- `check_mirrors` и preflight `publish`: ошибка проверки одного URL (включая неожиданное исключение) превращается
  в строку с проблемой этого URL и не прерывает проверку остальных; для неожиданного исключения код `internal_error`
  с типом исключения в деталях.

## F5. Календарные даты

- `manifest.schema_errors` дополнительно проверяет, что `issued_at` и `expires_at` — реальные даты UTC
  (`2026-02-30T12:00:00Z` → ошибка схемы). Так одинаково ведут себя `contract`, `sign` и `check`.
- `bin/check` и `bin/sign` на такой дате дают `invalid_manifest` с деталями, без traceback; остальные проверки `check` продолжаются.
- Утверждение `docs/client-contract.md` о совпадении машинной схемы и таблицы полей уточнить: календарную
  корректность даты JSON Schema не выражает, её проверяет код (референс и клиент).

## Уточнения контракта клиента (`docs/client-contract.md`)

1. **Замена базового домена в URL.** Хост `h` относится к базовому домену `b`, если `h == b` или `h` оканчивается на `"." + b`
   (сравнение без учёта регистра, после нормализации хоста). URL с другими хостами не переписываются.
   При совпадении заменяется суффикс `b` на активный домен, префикс поддомена сохраняется.
2. **Диапазон целых.** Все целые поля манифеста (`schema`, `version`, поля `policy`) ≤ `9007199254740991` (2^53 − 1):
   переносимо для JSON, Swift `Int` (64 бит) и Kotlin `Long`. Схема получает `maximum`; новые векторы:
   `version_max` (`version = 9007199254740991`, принят) и `version_overflow` (`9007199254740992`, `invalid_manifest`).
3. **Деградированный режим встроенного манифеста** (решение пользователя 2026-11-02). Если кеш не прошёл проверку,
   а встроенный манифест отвергнут только по `rollback` (его `version` ниже сохранённой), клиент использует встроенный
   манифест **только для выбора домена**: `stored_version` не понижается, встроенный не сохраняется в кеш,
   немедленно запускается загрузка с зеркал (объединение зеркал встроенного манифеста). Любой другой код отказа
   встроенного манифеста — ошибка сборки (тест на CI клиента обязан это ловить).
4. **Сетевые ограничения и сценарии этапа 2.** Клиент прекращает чтение ответа зеркала после 65536 байт и считает
   зеркало неудачным; ошибка разбора не должна ронять опрос остальных зеркал. Список обязательных тестов клиентского
   модуля (не JWS-векторы): `304 Not Modified` с ETag; выбор максимальной версии среди зеркал; одно зеркало отдаёт
   мусор/огромный ответ/таймаут; повреждённый кеш; деградированный режим п. 3; замена домена по п. 1, включая
   `evil-konsierge.com` (не совпадает с `konsierge.com`).

## Критерии приёмки

1. Регрессионные тесты (сначала красные на текущем коде):
   - F1: локальный bare-репозиторий как git-зеркало, оба env на v1, в рабочем репо закоммичены оба env v2;
     `publish.run(..., envs=("staging",))` → git-цель не пушит, `production` и `staging` строки git-цели — `env_filter_conflict`,
     bare-репозиторий не изменился; без `--env` — push, обе строки `upload ok`.
   - F2: preflight прочитал v1 и ETag; до записи объект подменён (v3); запись v2 → `error: conflict`, на хранилище v3.
     Новый объект: конкурентный писатель создал объект между preflight и записью → `conflict`.
   - F3: ответ `"[" * 10000 + "0" + "]" * 10000` → `malformed`; тело 70000 байт → `oversized`; в `check_mirrors`
     первое зеркало с аварийным ответом не мешает проверке остальных (их строки есть и корректны).
   - F5: `issued_at: "2026-02-30T12:00:00Z"` → `bin/check` `invalid_manifest` без traceback; `sign` отказывает; `contract` → `invalid_manifest`.
   - Векторы `version_max`, `version_overflow` в `testdata/`, raw-Ed25519 тест проходит.
2. `uv run pytest`, `uv run ruff check`, `uv run ruff format --check` зелёные; `bin/check` выход `0`; `bin/check-mirrors` выход `0`
   на живых зеркалах (манифесты не меняются, переподпись не нужна).
3. `docs/client-contract.md` содержит пп. 1–4; `README.md` описывает `conflict`, `env_filter_conflict`, `oversized`.

## Объём

Входит: F1, F2, F3, F5, уточнения 1–4, регенерация `testdata/`. Не входит: изменение манифестов и `dist/`, клиентские
библиотеки, CVE-аудит зависимостей, перенос мониторинга на `proxy`.
