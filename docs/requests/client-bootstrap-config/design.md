# Bootstrap-конфиг клиентов из независимых источников

Статус: черновик для обсуждения. Продолжение `traefik/docs/requests/dns-provider-resilience/proposal.md` (п. 9)
и `incident-2026-11-02.md` из того же пакета. Не привязан к Traefik: Traefik здесь только один из потребителей инвентаря доменов.
Этот репозиторий (`bootstrap`) и есть репозиторий манифестов из §5.

## Задача

Установленные клиенты (мобильные приложения, при желании SPA и десктоп) должны узнавать актуальные адреса
наших сервисов во время работы, а не из констант сборки. Смена или добавление домена — публикация файла,
а не релиз через сторы. Компрометация любого места хранения не должна позволять увести трафик.
Клиенты в основном в РФ: источники должны быть доступны оттуда и не падать одновременно.

Не решает: отказ самого API, блокировку всех наших доменов разом, компрометацию ключа подписи
(для него есть процедура ротации, но старые сборки остаются уязвимыми до обновления).

## Архитектура в одном абзаце

Один git-репозиторий — источник правды. В нём лежит человекочитаемый манифест `production.json`,
его подписанная копия (JWS, Ed25519, ключ офлайн у владельца) и список зеркал. CI проверяет подпись и схему,
раскладывает подписанный файл **байт в байт** на 4–6 независимых зеркал (RU object storage ×2–3,
GitHub, наш резервный домен, опционально Firebase Remote Config и push) и внешний монитор сверяет зеркала
с репозиторием. Клиент при старте опрашивает зеркала параллельно, принимает любой ответ с валидной подписью
и версией не ниже сохранённой, берёт максимальную версию, кеширует, и по манифесту выбирает живой базовый домен.
Сборка приложения содержит последний подписанный манифест как встроенный — у «нулевого дня» нет отдельного пути кода.

```
 владелец (офлайн-ключ)         git (GitLab + зеркало GitHub)              зеркала                  клиент
 ┌──────────────┐  sign   ┌──────────────────────────────┐  publish  ┌──────────────────┐  fetch   ┌──────────────┐
 │ production.  │ ──────► │ manifests/production.json    │ ────────► │ Yandex OS        │ ◄──────► │ verify sig   │
 │ json (правка)│         │ dist/production.jws  (подпись)│  CI или  │ Selectel OS      │          │ version ≥    │
 └──────────────┘         │ mirrors.yml, keys/, schema/  │  ноутбук  │ VK Cloud OS      │          │ max version  │
                          └──────────────────────────────┘           │ GitHub raw/Pages │          │ cache        │
                                      ▲                              │ ai-konsierge.ru  │          │ pick domain  │
                                      │ сверка                       │ (FCM push, FRC)  │          └──────────────┘
                              внешний монитор (Uptime Kuma на proxy) └──────────────────┘
```

## 1. Манифест

### Принципы

- **Манифест содержит только базовые домены** (решение 2026-11-02). Поддомены сервисов (`api`, `crm-api`, `files`, …)
  остаются в приложении: адрес = `<известный приложению host>.<base_domain>`. Это повторяет то, как Traefik зеркалит
  `x.konsierge.com ↔ x.ai-konsierge.ru`, и позволяет переписывать абсолютные URL из ответов backend заменой базового домена.
  Адреса, не укладывающиеся в схему (`gpb.pay.konsierge.com`, Sentry DSN, внешние SDK), тоже живут в приложении —
  в манифест они не выносятся, пока не понадобится менять их без релиза.
- **Один манифест на окружение, общий для всех приложений.**
  `production` и `staging` — разные файлы, разные ключи подписи (см. §2), клиент сверяет `env` со своим flavor.
- **Манифест переносит и свои зеркала.** Добавить зеркало можно без релиза; встроенный в сборку список — нижняя граница.
- **Размер ≤ 3,5 КБ** в подписанном виде: тогда манифест целиком помещается в FCM/APNs push (лимит 4 КБ).

### Схема (v1, черновик)

```json
{
  "schema": 1,
  "env": "production",
  "version": 42,
  "issued_at": "2026-11-02T12:00:00Z",
  "expires_at": "2027-05-02T12:00:00Z",
  "base_domains": ["konsierge.com", "ai-konsierge.ru"],
  "health_path": "/healthz",
  "mirrors": [
    "https://storage.yandexcloud.net/konsierge-bootstrap/v1/production.jws",
    "https://konsierge-bootstrap.selstorage.ru/v1/production.jws",
    "https://raw.githubusercontent.com/konsierge/bootstrap/master/dist/production.jws",
    "https://bootstrap.ai-konsierge.ru/v1/production.jws"
  ],
  "policy": {
    "connect_timeout_ms": 3000,
    "probe_interval_s": 600,
    "refresh_interval_s": 21600
  },
  "min_app_version": { "ios": "0", "android": "0" },
  "notice": { "ru": "", "en": "" }
}
```

Подписанный файл такого размера — около 1 КБ, запас до лимита push четырёхкратный.

Поля:

| Поле | Назначение |
| --- | --- |
| `schema` | мажорная версия формата; публикуется по пути `/v1/`, несовместимые изменения — новый путь `/v2/` и новый файл, старые клиенты продолжают читать `/v1/` |
| `version` | монотонный целый счётчик; защита от отката (клиент не принимает меньше сохранённого) |
| `issued_at`, `expires_at` | мягкий срок жизни (§3): влияет на предпочтение и алерты, не ломает клиент |
| `base_domains` | приоритет слева направо; первый — основной |
| `health_path` | путь пробы живости на хосте API при выборе домена |
| `mirrors` | где искать следующую версию |
| `policy` | таймауты и интервалы, чтобы менять поведение failover без релиза |
| `min_app_version` | мягкое требование обновления и текст для пользователя |
| `notice` | сообщение при инциденте, показывается без обращения к API |

Отложено: `tls.spki_pins` (пины CA, обновляемые без релиза) — только если в сборках появится pinning; `services` с явными `urls` —
если понадобится менять адрес вне схемы `<host>.<base_domain>` без релиза. Оба расширения совместимы со схемой v1: клиент игнорирует незнакомые поля.

## 2. Подпись

### Формат: JWS, JSON-сериализация, `alg: EdDSA` (Ed25519)

- **Один файл** `production.jws` вместо пары «json + sig»: нельзя получить манифест с одного зеркала,
  а подпись с другого и попасть в рассинхрон версий.
- **Подписываются байты payload, не разобранный JSON** — вопрос канонизации не возникает.
- **General JSON Serialization** допускает несколько подписей в одном файле: это нужно для переходного периода
  ротации (манифест подписан и старым, и новым ключом) и для порога 2-из-N, если он понадобится.
- Проверка не требует JOSE-библиотеки: Ed25519-verify над `ASCII(b64url(header) + "." + b64url(payload))`
  — 20 строк на любой платформе. Там, где JOSE-библиотека есть (`jose`, `jwcrypto`, `JWT` gem), можно использовать её.
- Protected header: `{"alg":"EdDSA","kid":"prod-2026a"}`. `kid` выбирает ключ из встроенного набора.

Почему не другое:

| Вариант | Почему нет |
| --- | --- |
| Sigstore/cosign keyless | онлайн-зависимость от Fulcio/Rekor за рубежом; для 3 КБ файла избыточно |
| Полный TUF | правильная модель (root/targets/timestamp, порог, отзыв), но 4 метафайла и клиентская библиотека на каждую платформу; берём из него свойства — монотонность, срок, набор ключей, — не формат. Путь апгрейда описан в §8 |
| minisign / signify | хорошие ключи, но нет клиентских библиотек на мобильных платформах; формат двух файлов |
| SSH-подписи (`ssh-keygen -Y`) | формат `sshsig` без мобильных библиотек |
| ECDSA P-256 | работает, но Ed25519 детерминирован, короче, без проблем с nonce; поддержка на всех платформах есть |
| Только TLS зеркала | зеркало или его CDN может подменить содержимое; TLS не защищает от компрометации хранилища |

### Ключи

- **Два ключа prod в каждой сборке**: активный `prod-2026a` и запасной `prod-2026b`. Манифест валиден,
  если подписан хотя бы одним ключом из встроенного набора (порог 1; порог 2 — опция в `policy`, когда появится второй подписант).
- **Ключ staging отдельный** (`stage-2026a`), им могут подписывать разработчики. Staging-сборки доверяют только staging-ключам,
  prod-сборки — только prod. Подмена окружения отсекается и ключом, и полем `env`.
- **Хранение prod-ключей** (решение 2026-11-02: файлы, без аппаратного токена): генерируются офлайн, приватный ключ зашифрован
  `age` с парольной фразой, копия в Passbolt и две офлайн-копии (USB/бумага) в разных местах. Запасной ключ хранится отдельно от активного
  и используется только при компрометации или утере активного. Держатель обоих — владелец.
- **CI не имеет ключей подписи вообще.** CI только проверяет подпись публичными ключами и публикует. Компрометация GitLab = компрометация зеркала, не больше.
- **Ротация плановая**: новый ключ добавляется в сборки → после достаточного охвата манифест подписывается старым и новым →
  через период старый убирается из подписи → из сборок. Сроки не фиксируем, ключи не истекают сами.
- **Компрометация активного ключа**: немедленно подписывать запасным, выпустить сборку с новым запасным.
  Сборки, где скомпрометированный ключ ещё в доверенном наборе, уязвимы до обновления — это и есть аргумент за `min_app_version` и за §8.

### Инструменты подписи

Без своего криптокода: `step crypto jwk create --kty OKP --crv Ed25519` для ключей и `step crypto jws sign` для подписи
(Smallstep CLI). Если удобнее скрипт в репозитории — `jwcrypto` (Python) или `jwt` + `rbnacl` (Ruby), 30 строк,
но тогда он же становится референсной реализацией. `bin/sign` принимает `manifests/<env>.json`, проверяет схему и монотонность
`version`, спрашивает парольную фразу, пишет `dist/<env>.jws`. `bin/verify` делает обратное и используется в CI, мониторинге и тестах клиентов.

## 3. Проверка целостности на клиенте

Манифест **принимается**, если одновременно:

1. хотя бы одна подпись верна под ключом из встроенного набора для этого окружения;
2. `env` совпадает с flavor сборки;
3. `schema` известна клиенту;
4. `version` ≥ сохранённой в защищённом хранилище (Keychain / EncryptedSharedPreferences) — защита от отката и от «замороженного» зеркала;
5. структура проходит валидацию (непустой `base_domains`, URL-ы парсятся, схемы только `https`/`wss`).

Срок (`expires_at`) **мягкий**: просроченный манифест используется, если ничего свежее не получено.
Обоснование: жёсткий срок превращает нашу забывчивость в отказ всех клиентов, а атака «заморозкой» уже отсечена монотонностью версии
и тем, что встроенный манифест не старше любого опубликованного на момент сборки. Единственный остаточный риск — домен,
перечисленный в ещё живом манифесте, выпал из регистрации и перехвачен; закрывается правилом эксплуатации:
**домены из любого манифеста за последние 3 года продлеваются**, а исключение домена из списка — отдельный осознанный шаг с бампом версии.
`expires_at` при этом даёт алерт мониторинга «переподписать» за 60 дней.

Кеш перепроверяется при каждой загрузке (устройство может быть рутовано, хранилище изменено). Встроенный манифест — такой же JWS,
проверяется тем же кодом.

Часы устройства в проверку не входят (кроме мягкого срока), чтобы сбитое время не ломало запуск.

### Алгоритм на старте

```
cached   = verify(load_cache()) or verify(embedded)
use(cached)                                    # приложение работает сразу
if cache_age > refresh_interval or last API error was DNS/connect:
    results = hedged_fetch(cached.mirrors ∪ embedded.mirrors, total_timeout = 5 s, stagger = 300 ms)
    best = max(version, [m for m in results if accept(m)])
    if best and best.version >= cached.version: save(best); use(best)
```

- Все зеркала опрашиваются параллельно (со ступенькой 300 мс, чтобы не бить по всем при здоровом первом),
  берётся **максимальная** версия среди валидных — отстающее по кешу зеркало (обычный случай) и враждебное
  застывшее зеркало (редкий) обрабатываются одинаково.
- `If-None-Match`/ETag: повторные запросы дешёвые; зеркала отдают `Cache-Control: max-age=300`.
- Любая ошибка DNS/соединения в основном HTTP-клиенте — триггер немедленного обновления манифеста и перевыбора домена.

### Выбор домена и переписывание URL

- Активный базовый домен один на приложение: по порядку `base_domains` пробуется `https://<api-host>.<domain><health_path>`
  с `connect_timeout_ms`; первый ответивший запоминается, все известные приложению поддомены строятся от него.
  Раз в `probe_interval_s` основной пробуется снова — возвращаемся на него автоматически.
- Абсолютные URL из ответов backend (картинки, файлы, ссылки оплаты, websocket): если хост оканчивается на любой из `base_domains`,
  базовый домен заменяется на активный. Параллельно backend переводится на относительные URL / генерацию от `Host`
  (`proposal.md` §9), после чего переписывание становится страховкой.
- Deep links, OAuth redirect, платёжные SDK в манифесте не участвуют — у них внешние регистрации; они покрываются двумя доменами на стороне провайдеров.

### Два слоя failover

1. **Мгновенный**: список `base_domains` уже в кеше/сборке — переключение на резервный домен происходит без сети к зеркалам.
2. **Управляемый**: манифест нужен, когда надо **добавить** или **переупорядочить** домены, выдать `notice`, поменять пины или таймауты.

Поэтому отказ всех зеркал одновременно не критичен: деградация до слоя 1.

## 4. Где хранить: зеркала

Критерии независимости — разные компания, DNS-провайдер имени зеркала, сеть (AS), юрисдикция, платёжный аккаунт, учётные данные публикации.
Минимум: одно зеркало в РФ-юрисдикции, одно вне её, одно на нашем резервном домене. Поскольку содержимое подписано,
зеркало не обязано быть доверенным — годится любой публичный HTTP, даже без TLS и по IP-литералу.

| Зеркало | Чей DNS/сеть | Из РФ | Публикация | Стоимость | Заметки |
| --- | --- | --- | --- | --- | --- |
| **Yandex Object Storage** `storage.yandexcloud.net` | Яндекс | да | S3 API, сервисный аккаунт с правом на один бакет | копейки | `proxy` уже в Yandex Cloud — аккаунт есть |
| **Selectel Object Storage** `*.selstorage.ru` / `s3.storage.selcloud.ru` | Selectel | да | S3 API | копейки | тот же провайдер, что и prod-сервер, — общий домен отказа с prod, но не с DNS |
| **VK Cloud Object Storage** `hb.ru-msk.vkcloud-storage.ru` | VK | да | S3 API | копейки | третий RU-провайдер; альтернатива — Timeweb Cloud S3, Cloud.ru |
| **GitHub** raw / Pages | GitHub/Fastly | да, периодически медленно | `git push` в зеркало репозитория | 0 | одновременно зеркало репозитория-источника; зарубежная юрисдикция |
| **Наш резервный домен** `bootstrap.ai-konsierge.ru` | Selectel DNS | да | тот же S3-бакет за CNAME или Traefik | 0 | коррелирует с инцидентами нашего DNS; быстрый путь в норме |
| **Третий домен-«маяк»** у третьего регистратора и DNS (например, `.app`/`.io` или второй `.ru`) | третий провайдер | зависит | CNAME на бакет | ~1–2 тыс. ₽/год | без продуктового трафика; разводит регистратора/DNS/TLD |
| **Firebase Remote Config** | Google | да, с риском замедления | REST API / консоль | 0 | SDK уже есть там, где есть FCM; значение параметра — тот же JWS-текст, ничего не доверяем Google |
| **FCM/APNs data push** | Google/Apple | да | скрипт рассылки | 0 | **push-канал**: подписанный манифест ≤ 3,5 КБ приходит всем сразу, без опроса; верифицируется тем же кодом |
| **IP-литерал по HTTP** `http://<ip>/v1/production.jws` | наш сервер | да | тот же бакет/nginx | 0 | последний рубеж, не зависит ни от какого DNS; подпись заменяет TLS; нужны исключения ATS/cleartext на один хост |
| CDN (Yandex CDN, EdgeCenter, Selectel CDN) | провайдер CDN | да | перед бакетом | по трафику | не нужен: 3 КБ × 4 запроса/день × 100 тыс. устройств ≈ 1,2 ГБ/день суммарно |

Отклонено: Telegram-канал как транспорт (нестабилен в РФ и тянет API-ключ в клиент), Cloudflare R2/Workers (доступность из РФ),
IPFS-шлюзы (доступность, латентность), DNS TXT как основной канал (размер, фильтрация резолверов; годится как указатель на зеркало, если понадобится).

**Принятый стартовый набор (решение 2026-11-02)**: Yandex Object Storage, Selectel Object Storage, GitHub raw,
`bootstrap.ai-konsierge.ru` как CNAME на один из бакетов (сертификат для своего домена выпускает менеджер сертификатов провайдера бакета).
Push-канал, VK Cloud и домен-маяк — после первого релиза. Все S3-бакеты — публичное чтение одного префикса `v1/`,
запись только сервисному аккаунту публикации, у каждого провайдера свой.

## 5. Управление в одном месте

Этот репозиторий, `bootstrap`: GitLab `digitalbox/backend/instruments/bootstrap` — источник,
GitHub `konsierge/bootstrap` — зеркало и одновременно раздача через raw (решение 2026-11-02):

```
manifests/production.json   manifests/staging.json     # источник, правится руками / инвентарём
dist/production.jws         dist/staging.jws           # подписанные, коммитятся — это и есть публикуемые байты
keys/prod-2026a.pub.json    keys/prod-2026b.pub.json   keys/stage-2026a.pub.json   # JWK, их же встраивают клиенты
schema/manifest.v1.json                                 # JSON Schema
mirrors.yml                                             # цель → тип (s3/git/firebase) → ссылка на секрет
bin/sign  bin/verify  bin/publish  bin/check-mirrors
testdata/                                               # векторы: валидный, битый payload, чужой ключ, откат версии, чужой env, просроченный
```

Поток изменения:

1. Правка `manifests/production.json`, `version += 1` — MR.
2. Владелец: `bin/sign production` — парольная фраза, в `dist/` новый JWS. Коммит в тот же MR.
3. CI на MR: схема; `version` строго больше того, что сейчас на зеркалах; `bin/verify` публичными ключами из `keys/`;
   каждый URL из манифеста резолвится и отвечает на `health` (предупреждение, не блок — в инцидент часть хостов мертва по определению).
4. CI на `master`: `bin/publish` раскладывает `dist/*.jws` байт в байт во все цели из `mirrors.yml` с `Cache-Control: max-age=300`,
   затем скачивает с каждого зеркала и сравнивает с `dist/`.
5. **Аварийный путь без GitLab**: тот же `bin/publish` с ноутбука, учётные данные публикации — из Passbolt/локального `age`-файла.
   Ни один шаг не зависит от `konsierge.com`.

Сборки приложений на CI забирают `dist/<env>.jws` (с GitHub-зеркала или как git-submodule) и кладут в ресурсы — встроенный манифест
всегда равен последнему подписанному на момент сборки.

Мониторинг — **вне infra** (Uptime Kuma на `proxy` + `bin/check-mirrors` по cron там же): каждые 5 минут для каждого зеркала —
HTTP 200, подпись валидна, `version` равна `dist/` в репозитории, `expires_at − now > 60 дней`. Алерт в канал, не зависящий от нашего домена.

Сценарий инцидента: правка порядка `base_domains` → подпись → публикация — 5 минут. Клиенты с падающими запросами обновятся
немедленно (триггер по ошибке), остальные — при следующем старте или через `refresh_interval_s`; при необходимости — push.

## 6. Модель угроз

| Угроза | Чем закрыта |
| --- | --- |
| Компрометация зеркала или его учётных данных | подделать нельзя (нет ключа); застывшая версия проигрывает максимуму по остальным зеркалам и монотонности; отказ — остальные зеркала и кеш |
| Компрометация GitLab/CI | CI не подписывает; эквивалентно компрометации всех зеркал разом: клиенты остаются на кеше/встроенном манифесте; монитор ловит расхождение с `dist/` |
| MITM/подмена в сети (включая DPI) | подпись не зависит от TLS; HTTPS остаётся для приватности и CDN |
| Откат на старый манифест | монотонная `version`, хранение в защищённом хранилище |
| Подмена окружения (staging-манифест в prod-сборке) | раздельные ключи + поле `env` |
| Компрометация staging-ключа у разработчика | затрагивает только staging-сборки |
| Компрометация prod-ключа | запасной ключ + релиз; старые сборки уязвимы до обновления (остаточный риск, см. §8) |
| Утеря prod-ключа | запасной ключ в сборках, офлайн-копии обоих |
| Перехват нашего домена (регистратор) | атакующий с DNS получает и сертификат — это компрометация API независимо от манифеста; манифест позволяет увести клиентов на другой домен за минуты; если появится pinning, пины `spki_pins` можно будет сузить без релиза |
| Домен из старого манифеста выпал из регистрации | правило эксплуатации «продлевать 3 года», исключение домена — осознанный шаг |
| Модифицированный кеш на рутованном устройстве | кеш перепроверяется подписью при каждой загрузке |
| Утечка метаданных | зеркала видят IP пользователей и факт использования приложения; GitHub — зарубежный. Содержимое манифеста публично и не секретно по замыслу |

## 7. Клиентская часть

Клиенты — нативные iOS (Swift) и Android (Kotlin) (решение 2026-11-02). Одна спецификация (этот документ + `schema/` + `testdata/`),
две реализации — тонкий слой: fetch с хеджированием, verify, кеш, выбор домена, переписывание URL, хук в HTTP-клиент
(`URLSession`/OkHttp interceptor). Оценка — 3–5 дней на платформу вместе с интеграцией.

| Платформа | Ed25519 | Хранилище версии и кеша |
| --- | --- | --- |
| iOS/Swift | CryptoKit `Curve25519.Signing` (iOS 13+) | Keychain |
| Android/Kotlin | Tink или BouncyCastle (`java.security.Signature("Ed25519")` в платформе только на новых API-уровнях) | EncryptedSharedPreferences |

Web SPA вне объёма: при необходимости та же схема применима через `@noble/ed25519`, заменяя build-time `VITE_*`/`REACT_APP_*` адреса runtime-конфигом.

Тест-векторы из `testdata/` гоняются на каждой платформе в unit-тестах; на staging — chaos-прогон: поменять порядок `base_domains`,
убедиться, что клиенты переехали и вернулись после отката.

## 9. Решения

Принято 2026-11-02:

1. Клиенты — нативные Swift и Kotlin; SPA вне объёма.
2. Зеркала первой итерации — Yandex Object Storage, Selectel Object Storage, GitHub raw, `bootstrap.ai-konsierge.ru` CNAME на бакет.
3. Prod-ключи — файлы `age` у владельца, копия в Passbolt, две офлайн-копии; аппаратный токен не используется.
4. Отдельный репозиторий `bootstrap`: GitLab `digitalbox/backend/instruments/bootstrap`, GitHub-зеркало `konsierge/bootstrap`.
5. Push-канал — после первого релиза.
6. Манифест содержит только базовые домены; поддомены сервисов знает приложение.

7. Certificate pinning в мобильных сборках отсутствует (подтверждено мобильной командой 2026-11-02). Не вводить: системное доверие плюс
   Certificate Transparency достаточны, а пиннинг заблокировал бы резервный домен и смену CA. Если защита от подставных CA понадобится,
   пины вводятся только через манифест (`tls.spki_pins`, fail-open при недоступности) — не в код приложения.

Открыто:

- Интервалы по умолчанию (`refresh_interval_s` 6 ч, `connect_timeout_ms` 3000, `probe_interval_s` 600) — приняты как стартовые, меняются манифестом без релиза.
